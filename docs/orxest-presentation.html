Orxest · project-centric orchestration for AI-assisted development

Create a project.
Decide which agents work on it.

Orxest is not a coding agent. It is the control plane that turns software work into executable tasks, picks the right agent for every workflow step and keeps the history.

Agents perform work. Orxest decides how work moves through the system.

Two things people mix up
ConceptScopeWhat it is
Agent configurationglobalharness + provider + model + reasoning + limits. Reusable everywhere.
Assignmentper projectagent × role × priority × enabled. “This agent may serve this role in this project.”
Roleglobalarchitect, senior-developer, tester, reviewer, … Workflow steps require roles, never agents.
You do not “assign a project to an agent”. The project owns the assignments: the same agent can be a junior-developer in one project and a senior-developer in another — with a different model if you like.

The task itself has no role, agent or model

A task moves through workflow steps; each step requires a role, and Orxest selects an enabled agent for that role at that moment. That is why one task can be handled by four different agents:

Before you start

Four things you need

≈ 5 minutes
1A running Orxest
# one binary, one SQLite file, the web console included
make build
./bin/orxest serve          # → http://127.0.0.1:8787
2A Git repository (or a path for a new one)

An existing checkout on the Orxest host, or tick Initialise a new repository and Orxest runs git init plus an initial commit for you.

3A coding-agent CLI

Pi or Codex on PATH, authenticated, with the provider keys in the environment that starts Orxest — credentials are never stored in the database.

pi --list-models        # what Pi can use
pi --version
4At least one agent configuration

Create them on the Agents page first, or add them inline while creating the project — both write the same records.

No sandbox by default. Pi documents that its tools run with the permissions of the Orxest process. For unattended runs on untrusted repositories, run Orxest inside a container or VM.

What each field decides

  • Repository path — the only directory tree Orxest and its agents run in. Each task gets a worktree under <repo>/.orxest/worktrees/.
  • Target branch — where approved task branches are merged. Orxest switches your checkout to it when integrating.
  • Repository URL — used when the path does not exist yet and Orxest clones instead of initialising.

After saving

Orxest prepares the repository (detecting its default branch), returns a repository_status, and takes you to the project’s Board tab. A repository problem — a path that is not a Git repository, a missing URL — arrives as a warning toast rather than a lost project, and GET /api/projects/<id>/repository re-checks it whenever you like.

Read the template as a staffing list. Every step names a role. If a role has no enabled agent when a task reaches that step, Orxest blocks the task with policy_failure and tells you which role is missing — it never guesses.

Branching is part of the template

In standard, failing tests send the task back to implementation instead of failing it; the review step is an approval gate, so a human (or the API) approves or rejects before integration.

Only orchestration-relevant settings

Orxest deliberately exposes harness, provider, model, reasoning level and execution limits. Inference tuning (temperature, top_p, top_k, min_p, repetition penalty) belongs to the model provider and is not part of Orxest.

Why reasoning is a separate knob

Give junior-developer a cheap model with reasoning: low and senior-developer a strong one with high — the role/agent split is exactly what makes that trade-off a configuration change instead of a code change.

Harness options stay per harness

For Pi: tools, exclude_tools, config_dir, project_trust, sessions, arg:<flag>. For Codex: sandbox, profile, config.

Selection

How Orxest picks the agent for a step

deterministic · explainable

The rules, in order

1the workflow step’s role
2assignments for that role that are enabled, with an enabled agent
3the agent’s harness is registered in this deployment
4the agent has capacity (max_concurrent_executions)
5project limit, then global limit allow another execution
6highest assignment priority wins; ties break on name

No agent for the role

Task → blocked policy_failure
“no enabled agent is configured for role reviewer”.
Assign one and it resumes by itself.

All agents busy

The task stays ready and waits for the next scheduler tick — a temporary condition, not a failure.

What you see in the log

# every dispatch records the decision
task dispatched   task_id=tsk_…  step=implementation
                  role=developer agent=pi-senior
                  harness=pi model=gemini-2.5-pro reasoning=high

Human override, always available

  • Reassign — point the next execution at a specific agent.
  • Move — send the task to another workflow step.
  • Retry — new execution, previous ones preserved.
  • Approve / Reject — at an approval gate, so review is a real gate.

What you get for free per task

  • an isolated worktree and branch orxest/task/<id>
  • live streamed output and a raw JSONL harness log
  • append-only execution history with the agent, model and outcome of every attempt
  • token and cost metrics reported by the harness
  • rework loops, retries and a merge into the target branch on approval

Where to look when something is stuck

Task view → status, current step, current agent, blocked reason, failure kind, dependency statuses and the full execution history. Every state change carries a timestamp.

Recap

New project in four moves

1Create the project

Name it, point it at a repository path, choose the target branch. Or start a brand-new repository from the same form.

2Pick the workflow template

The template tells you exactly which roles must be staffed — minimal, standard or production to begin with.

3Configure agents

Globally on Agents, or inline in the creation form: harness, model, reasoning, limits. Reuse the same configuration across projects.

4Assign them to the project’s roles

Project → Agents tab. One assignment per role (or several with priorities). That is the link between a workflow step and a worker.
